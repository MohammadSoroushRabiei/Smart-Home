## ۸. نکات فنی مهم برای فیچرهای TLS/HTTPS آینده 🔐

- **`esp_https_server`: نام فیلد گواهی سرور `config.servercert`/`config.servercert_len` است، نه `config.cacert_pem`/`config.cacert_len`.** فیلد `cacert_pem` برای گواهی/CA سمت کلاینت است (mutual-TLS)، نه گواهی خود سرور — استفاده‌ی اشتباه از آن باعث خطای گمراه‌کننده‌ی «No Server certificate supplied» می‌شود در حالی که طول/محتوای گواهی کاملاً درست است.
- **`EMBED_TXTFILES` symbol naming:** نام symbol تولیدشده بر اساس مسیر کامل نسبی فایل است (مثلاً `certs/servercert.pem` → `_binary_certs_servercert_pem_start` در برخی حالات build)؛ اگر لینکر خطای `undefined reference` داد، با `nm` روی فایل `.obj` مربوطه نام دقیق symbol را چک کن به‌جای حدس زدن.
- **کمبود DRAM داخلی حین TLS handshake:** روی ESP32-S3 با بار همزمان مدل‌های esp-dl + بافرهای LVGL + Wi-Fi، mbedtls برای تخصیص بافرهای handshake (۱۶+ کیلوبایت) با DRAM داخلی به مشکل می‌خورد (خطای `PSA_ERROR_INSUFFICIENT_MEMORY` / کدهای مشابه `-0x008D`). **راه‌حل:** `Component config → mbedTLS → Memory allocation strategy → External SPIRAM` (یا `CONFIG_MBEDTLS_EXTERNAL_MEM_ALLOC=y` در `sdkconfig.defaults`) — از همان ۸ مگابایت PSRAM موجود روی برد استفاده می‌کند. **این تنظیم را قبل از هر فیچر TLS دیگری (مثلاً MQTT روی TLS برای ThingsPod/HA) از ابتدا فعال نگه دار.**
- خطاهای پراکنده‌ی `mbedtls_ssl_handshake returned -0x7780` (`MBEDTLS_ERR_SSL_FATAL_ALERT_MESSAGE`) از سمت کلاینت‌هایی مثل probe های پس‌زمینه‌ی مرورگر/سیستم‌عامل طبیعی هستند و نیازی به رفع ندارند، تا وقتی درخواست‌های واقعی (`/capture`, `/api/face/*`, `/password`) با موفقیت انجام می‌شوند.
- **`max_uri_handlers` پیش‌فرض `esp_https_server` فقط ۸ است.** با اضافه شدن هر هندلر جدید (مثلاً `/password` و `/api/password`)، اگر از ۸ رد شوی، `httpd_register_uri_handler` برای هندلرهای اضافه به‌صورت **خاموش (silent)** fail می‌شود — یعنی نه بیلد ارور می‌دهد نه لاگ خطا (مگر اینکه مقدار برگشتی‌اش را چک کنی)، و فقط موقع درخواست واقعی به آن مسیر، یک 404 مبهم می‌بینی. **قاعده‌ی کلی:** هر بار که یک URI handler جدید اضافه می‌کنی، `config.httpd.max_uri_handlers` را با تعداد واقعی هندلرها + کمی حاشیه (مثلاً +۳) هماهنگ نگه دار، و مقدار برگشتی `httpd_register_uri_handler` را همیشه چک/لاگ کن تا این نوع باگ دیگر silent نماند.

## ۹. نکات فنی مهم برای فیچر Home Assistant / Docker 🏠

- **انتخاب Docker Desktop به‌جای WSL2 دستی:** چون Docker Desktop با WSL2 backend، پورت‌های `publish`شده‌ی container را مستقیماً روی IP واقعی ویندوز در شبکه‌ی محلی هم در دسترس می‌گذارد، مشکل معمول NAT داخلی WSL2 (که در آن دستگاه‌های دیگر شبکه نمی‌توانند مستقیم به IP داخلی WSL2 وصل شوند) خودکار حل می‌شود. برای تست اولیه‌ی سریع، این از تنظیم دستی `mirrored networking` در `.wslconfig` ساده‌تر است.
- **`ha-config/` و `mosquitto/data/`, `mosquitto/log/` باید در `.gitignore` باشند:** این پوشه‌ها با `volumes:` در `docker-compose.yml` به دیسک ویندوز مپ می‌شوند تا تنظیمات HA (پسورد ادمین، توکن‌ها، دیتابیس تاریخچه) و داده‌های Mosquitto حتی بعد از پاک/rebuild شدن container باقی بمانند — اما محتوایشان حساس است و نباید وارد Git شود.
- **Mosquitto بدون `mosquitto.conf` هیچ پورتی listen نمی‌کند:** برخلاف انتظار، ایمیج پیش‌فرض `eclipse-mosquitto` بدون یک فایل کانفیگ صریح (حتی حداقلی، فقط `listener 1883` + `allow_anonymous true` برای تست) روی هیچ پورتی گوش نمی‌دهد و اتصال با خطای «Failed to connect» رد می‌شود. کانفیگ فقط موقع **start شدن** container خوانده می‌شود؛ اگر فایل را بعد از اولین `up` اضافه/ویرایش کردی، باید `docker compose restart mosquitto` (یا `down` + `up`) بزنی.
- **MQTT integration در HA به broker با اسم سرویس Docker وصل می‌شود، نه IP:** چون `homeassistant` و `mosquitto` هر دو در همان `docker-compose.yml` و همان Docker network مشترک هستند، در فرم HA برای Broker باید نام سرویس (`mosquitto`) وارد شود، نه `localhost` یا یک IP — Docker خودش DNS داخلی برای resolve این اسم دارد.
- **تصمیم معماری: MQTT Discovery به‌جای تعریف دستی entity در `configuration.yaml`:** چون چند entity (light, sensor×3, lock) داریم، Discovery (پیام JSON معرفی که ESP32 قبل از publish کردن state می‌فرستد) نگهداری را ساده‌تر می‌کند؛ افزودن entity جدید فقط نیاز به تغییر فرم‌ور دارد، نه دست‌زدن به تنظیمات HA.
