## ۲. انجام‌شده ✅

- LCD ST7796 + LVGL، تاچ GT911، BME280، LED/دکمه فیزیکی، SPIFFS
- Wi-Fi + retry، HTTP server
- پایپ‌لاین Edge-AI تشخیص چهره (JPEG → `esp_jpeg` → detect → recognize)
- پردازش async چهره (صف FreeRTOS + worker جدا)
- `app_state` مرکزی thread-safe
- HTTPS با گواهی self-signed embed‌شده
- سیستم رمز عبور کامل (`password_manager` + کیبورد LCD + `/password`)
- Home Assistant + Mosquitto (Docker) + فرم‌ور MQTT کامل با Discovery (۶ entity)
- قفل فیزیکی سلونوئیدی کامل (رله GPIO21، fail-secure، دو-لایه relock)
- فیکس UX کیبورد LCD (Back button، فونت، فیدبک)
- فیکس کرش I2C (mutex مشترک بین BME280 و تاچ)
- **✅ جداسازی کامل Enroll/Recognize + مدیریت چهره‌ها (`feature/enroll-token-auth`):**
  - `/recognize` باز و بدون احراز هویت (طبق طراحی - هرکسی می‌تواند تلاش کند وارد شود، مدل تصمیم می‌گیرد)
  - `/enroll?token=XXXX` پشت توکن یک‌بارمصرف ۶ رقمی (۳ دقیقه اعتبار)، تولید فقط از صفحه‌ی Settings روی LCD (بعد از تایید رمز)
  - **اعتبارسنجی توکن هم روی GET هم روی POST:** اگر توکن نامعتبر/منقضی باشد، صفحه‌ی `/enroll` اصلاً لود نمی‌شود (صفحه‌ی "Link expired" نشان داده می‌شود)؛ اگر توکن حین کار کاربر منقضی/کنسل شود، صفحه‌ی از‌قبل‌لودشده باز می‌ماند ولی خود درخواست ثبت (POST) رد می‌شود
  - صفحه‌ی مستقل Settings روی LCD (`settings_screen.c/.h`) با QR داینامیک + شمارش معکوس زنده + دکمه‌ی Back که توکن را باطل می‌کند
  - **رفع باگ همیشگی `enroll` که `id=1` برمی‌گرداند:** چون خود کتابخانه (`HumanFaceRecognizer::enroll` و حتی `DataBase::enroll_feat` سطح پایین‌تر) هیچ ID ای برنمی‌گرداند، بلافاصله بعد از enroll موفق یک self-recognize روی همان تصویر انجام می‌شود تا ID واقعی خوانده شود
  - **ماژول جدید `face_db.c/.h`:** چون کتابخانه هیچ متد public ای برای لیست کردن چهره‌های ثبت‌شده ندارد، یک نگاشت `id ↔ نام` مستقل در NVS نگه داشته می‌شود
  - اسم‌گذاری از صفحه‌ی وب `/enroll` (گوشی کاربر - کیبورد کامل)، نه از LCD (کیبورد فقط عددی)؛ دکمه‌ی Enroll تا خالی بودن نام غیرفعال است
  - صفحه‌ی «Manage Faces» روی LCD: لیست id+نام + حذف با تایید (`lv_msgbox`)
  - پاسخ Recognize حالا اسم واقعی نشان می‌دهد ("Welcome, Ali") به‌جای ID خام
- `.gitignore`، شاخه‌های فیچر به `main` merge شدند

## ۳. ⚠️ ریسک‌های امنیتی شناخته‌شده و آگاهانه پذیرفته‌شده

این پروژه دیگر یافته‌ی امنیتی «بحرانی و حل‌نشده» ندارد، ولی دو ریسک کوچک‌تر و کنترل‌شده به‌صورت آگاهانه برای صرفه‌جویی در وقت (با توجه به بودجه‌ی باقی‌مانده) پذیرفته شدند. هر دو باید صادقانه در دفاع قابل توضیح باشند:

### ۱. رکوردهای «یتیم» (orphan) در دیتابیس تشخیص چهره
اگر به هر دلیلی (مثلاً داده‌ی تستی قدیمی از قبل از پیاده‌سازی `face_db`) تعداد چهره‌های واقعی در دیتابیس کتابخانه (`get_num_feats()`) بیشتر از تعداد رکوردهای نام‌دار در `face_db` باشد، آن چهره‌های اضافی **در سیستم قابل‌مشاهده نیستند ولی همچنان می‌توانند قفل را باز کنند** - چون منطق `recognize()` مستقل از `face_db` کار می‌کند.
- **چرا حل نشد:** تنها راه امن برای پاک کردن **فقط** رکوردهای یتیم (بدون از دست دادن چهره‌های معتبر) نیاز به یک اسکن ID به ID با فراخوانی‌های `delete_feat()` روی IDهای نامعلوم دارد که رفتارشان (موفق/خطا/احتمال کرش) بدون دیدن سورس داخلی کتابخانه تضمین‌شده نیست - ریسک باگ‌زایی بیشتر از فایده‌اش در بودجه‌ی فعلی تشخیص داده شد.
- **راهکار پذیرفته‌شده:** قبل از ارائه/دفاع، یک‌بار به‌صورت دستی کل NVS/SPIFFS پاک می‌شود (`idf.py erase-flash` یا معادلش) و فقط چهره‌های معتبر و لازم دوباره enroll می‌شوند. از این لحظه به بعد، چون هر enroll/delete هم‌زمان `face_recognition` و `face_db` را آپدیت می‌کند، دیگر نباید mismatch رخ دهد.
- **TODO برای فرصت بعدی (اگر وقت اضافه آمد):** پیاده‌سازی همان اسکن ID-به-ID با تست دقیق روی رفتار `delete_feat()` روی ID نامعتبر، احتمالاً با یک نسخه‌ی آزمایشی جدا قبل از اعمال در فرم‌ور اصلی.

### ۲. بدون محافظت در برابر حدس زدن (brute-force) توکن Enroll
توکن ۶ رقمی (۱ میلیون حالت، ۳ دقیقه اعتبار) در حال حاضر هیچ محدودیتی روی تعداد تلاش‌های ناموفق ندارد. تصمیم گرفته شد این محافظت (مثلاً باطل کردن خودکار توکن بعد از N تلاش اشتباه) اضافه نشود.
- **چرا پذیرفته شد:** ریسک عملی محدود است - مهاجم باید هم روی شبکه‌ی محلی خانه باشد هم در بازه‌ی ۳ دقیقه‌ای که کاربر عمداً توکن تولید کرده، هزاران درخواست بفرستد؛ و حتی موفق، فقط به enrollment (نه unlock مستقیم) دسترسی می‌دهد - قفل واقعی هنوز نیاز به authentication دومرحله‌ای (چهره یا رمز) دارد.
- **TODO برای فرصت بعدی:** افزودن شمارنده‌ی تلاش ناموفق (طرح آماده، پیاده‌سازی‌نشده) در صورت وجود وقت اضافه.

## ۹. نکات فنی TLS/HTTPS 🔐

- `config.servercert`/`config.servercert_len` نه `cacert_pem`
- `EMBED_TXTFILES` symbol naming بر اساس مسیر نسبی فایل
- `CONFIG_MBEDTLS_EXTERNAL_MEM_ALLOC=y` برای کمبود DRAM حین handshake
- `max_uri_handlers` پیش‌فرض ۸ - با هر هندلر جدید هماهنگ نگه دار

## ۱۰. نکات فنی Home Assistant / Docker / MQTT 🏠

- Docker Desktop روی ویندوز پورت‌ها را روی IP واقعی هم expose می‌کند
- `ha-config/`, `mosquitto/data/`, `mosquitto/log/` در `.gitignore`
- Mosquitto بدون `mosquitto.conf` هیچ پورتی listen نمی‌کند
- MQTT integration در HA به broker با اسم سرویس Docker وصل می‌شود، نه IP
- `esp-mqtt` کامپوننت built-in است؛ فقط نیاز به `PRIV_REQUIRES "mqtt"`
- معماری قفل دو-لایه: `lock.c` گنگ (فقط رله + fail-safe مستقل)؛ `app_state.c` تنها نقطه‌ی ورودی رسمی
- `binary_sensor` به‌جای `lock` کامل برای وضعیت قفل (تصمیم امنیتی تا امن شدن Mosquitto)
- `event` entity به‌جای `binary_sensor` برای رویدادهای دسترسی

## ۱۱. نکات فنی باس I2C مشترک 🔌

- مشکل: race condition بین `sensor_task` و `touch_poll_task` روی باس مشترک، بدون timeout داخلی در درایور GT911
- راه‌حل: mutex اپلیکیشنی (`i2c_bus_lock`/`i2c_bus_unlock`) دور هر تراکنش منطقی
- قاعده: هر تابعی که lock می‌کند، باید در **همه‌ی** مسیرهای خروج unlock کند (الگوی `bool success` + یک نقطه‌ی خروج)

## ۱۲. نکات فنی enrollment و مدیریت چهره 🔐

- **`HumanFaceRecognizer::enroll()` هیچ ID برنمی‌گرداند** (فقط `esp_err_t`) — حتی `DataBase::enroll_feat()` سطح پایین‌تر هم همینطور. برای گرفتن ID واقعی، بلافاصله بعد از enroll موفق باید همان تصویر را یک‌بار `recognize()` کرد و ID را از آنجا خواند.
- **کتابخانه هیچ متد public ای برای لیست کردن چهره‌های ثبت‌شده ندارد** (`DataBase` فقط `print()` دارد که مستقیم لاگ می‌کند، نه یک مقدار قابل‌استفاده در UI). برای این نیاز، باید یک لایه‌ی متادیتای مستقل (این پروژه: `face_db.c/.h` روی NVS) نگه داشته شود.
- **اسم‌گذاری چهره باید از دستگاهی با کیبورد کامل بیاید، نه از کیبورد عددی LCD** — چون فرآیند enroll از قبل روی مرورگر گوشی کاربر انجام می‌شود (`/enroll?token=XXXX`)، طبیعی‌ترین محل برای فیلد نام هم همان‌جاست.
- **اعتبارسنجی توکن باید هم روی GET (لود صفحه) هم روی POST (ثبت واقعی) انجام شود**، نه فقط POST - وگرنه صفحه‌ی enroll بدون هیچ محدودیتی برای هرکسی لود می‌شود (حتی اگر عملاً کاری نتواند بکند، جای بهتری برای مسدودسازی زودهنگام وجود دارد).
- **دو ریسک امنیتی باقی‌مانده (orphan records، brute-force توکن) به‌صورت آگاهانه پذیرفته شدند** با راهکار دستی/موقت - جزئیات کامل در بخش ۳.
